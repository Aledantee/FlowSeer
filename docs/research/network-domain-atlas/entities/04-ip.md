## ip-address

**What it is.** The IP addresses configured on an interface, with prefix length,
origin, and status.

### Canonical models

Two generations, and both are usually present:

| Table | Key | Status |
|---|---|---|
| `RFC1213-MIB` / `IP-MIB::ipAddrTable` | `ipAdEntAddr` | **deprecated**, IPv4 only, `ipAdEntNetMask` as a dotted mask, one address per row keyed *globally by address* |
| `IP-MIB::ipAddressTable` (RFC 4293) | `ipAddressAddrType, ipAddressAddr` | current, family-agnostic. `ipAddressIfIndex`, `ipAddressType` (unicast/anycast/broadcast), `ipAddressPrefix` (a pointer into `ipAddressPrefixTable`), `ipAddressOrigin` (other/manual/dhcp/linklayer/random), `ipAddressStatus` (preferred/deprecated/invalid/inaccessible/unknown/tentative/duplicate/optimistic), `ipAddressCreated`, `ipAddressLastChanged` |
| `IP-MIB::ipAddressPrefixTable` | `ifIndex, prefixType, prefix, prefixLength` | the prefix itself, with `ipAddressPrefixOnLinkFlag`, `AutonomousFlag`, and the RA lifetimes |
| `IPV6-MIB::ipv6AddrTable` / `ipv6AddrPrefixTable` | `ipv6IfIndex, ...` | **obsolete**, superseded by `ipAddressTable`; still the only IPv6 source on older agents |
| `openconfig-if-ip` | `subinterfaces/subinterface/ipv4/addresses/address[ip]` | `config/{ip, prefix-length}`, `state/origin` |
| `ietf-ip` (RFC 8344) | `interfaces/interface/ipv4/address[ip]` | `netmask` or `prefix-length` as a choice |

**The key difference that matters:** the deprecated table is keyed on the
address alone, the current one on (family, address). Neither is keyed on the
interface — you read `ipAddressIfIndex` as a column. So the same address
appearing on two interfaces is unrepresentable, which is correct, but it also
means you cannot walk "addresses of interface X" without walking everything.

SNMP::Info's `ip_index` / `ip_table` / `ip_netmask` methods fall back from
`ipAddrTable` to `ipAddressTable` transparently. That dual-source fallback is
the single most reusable pattern in this record.

### Vendor mapping

| Family | Surface |
|---|---|
| IETF | `IP-MIB` both generations, `IPV6-MIB` |
| Cisco SMB | `CISCOSB-rlIP-MIB::rlIpAddressTable [AUGMENTS ipAddressEntry]` and a second `rlIpAddressTable[addrType, addr, origin, generalPrefixName]` — note **origin in the key**, so the same address from two sources is two rows |
| Comware | `HH3C-IP-ADDRESS-MIB`: `hh3cIpAddrSetTable[ifIndex, addrType, addr]` (write) and `hh3cIpAddrReadTable[ifIndex, addrType, addr]` (read) — a deliberate read/write split; plus `HH3C-IPV6-ADDRESS-MIB` |
| Huawei | `HUAWEI-IF-EXT-MIB::hwIfIpAddrTable[ifIndex, addr]`, `hwIfIpTable[hwIpAdEntAddr]`, `hwIfIpUnnumberedTable[ifIndex]` (**unnumbered interfaces**, which nothing else models) |
| HP ProCurve | `HP-ICF-IPCONFIG::hpicfIpAddrTable[ifIndex, addr]`, `hpicfIpConfigTable[ifIndex]` |
| D-Link | `DLINKSW-IP-EXT-MIB::dIpExtIpAddressTable[addrType, address, ifIndex]` |
| FASTPATH family | `agentIpv6AddrTable[ifIndex, address]`, `agentIpv6AddrPrefixTable[ifIndex, prefix, prefixLength]`, `agentNetworkIpv6AddrTable[prefix]` (the management "network port"), `agentServicePortIpv6AddrTable` (the OOB service port) — **three separate address namespaces**, which is a real modelling hazard |
| LANCOM LCOS | `lcsStatusIpv6AddressesTable[interfaceName, ipv6Address]` |
| LANCOM LX | `lcosLXStatusIPConfigurationAddresses[interfaceName, ipVersion, addressSource, address]` — source in the key again |
| Ruckus ICX | `openconfig-if-ip` |

### Traps and pitfalls

- **Secondary addresses.** IPv4 secondaries are separate rows with the same
  `ipAddressIfIndex`; nothing marks which is primary. Several vendors care
  (source-address selection) and none report it in a standard object.
- **`ipAddressOrigin` conflates two things** for IPv6: how the address was
  *assigned* (manual, DHCPv6, SLAAC) and how the interface identifier was
  *generated* (EUI-64 from the link layer, or RFC 7217/privacy-random).
  FlowSeer's net-core research spotted this and calls for a corrected taxonomy.
  The corpus supports that: `linklayer(4)` and `random(5)` are both really
  "SLAAC, with different IID generation".
- Link-local addresses appear in `ipAddressTable` and are not routable
  identities. Almost every "device IP" heuristic has to exclude `fe80::/10`.
- The management/service-port split in the FASTPATH lineage means the OOB
  address is *not* in `ipAddressTable` on those devices.

### FlowSeer status

`net/ip/v1/interface_address.proto`, `address_origin.proto`,
`address_status.proto`, `ip_facet.proto` + `ipv4_facet` / `ipv6_facet`. The
family-equality invariant on the address row is retained. Good coverage. The
origin taxonomy fix is flagged and not yet done.

## arp-nd

**What it is.** The IP-to-MAC resolution cache: ARP for IPv4, Neighbour
Discovery for IPv6. Together with the [FDB](03-switching.md#fdb) this is how you
answer "what is that device and where is it".

### Canonical models

| Table | Key | Status |
|---|---|---|
| `RFC1213-MIB` / `IP-MIB::ipNetToMediaTable` | `ipNetToMediaIfIndex, ipNetToMediaNetAddress` | **deprecated**, IPv4 only. `ipNetToMediaPhysAddress`, `ipNetToMediaType` (other/invalid/dynamic/static) |
| `IP-MIB::ipNetToPhysicalTable` (RFC 4293) | `ifIndex, netAddressType, netAddress` | current. `ipNetToPhysicalPhysAddress`, `ipNetToPhysicalLastUpdated`, `ipNetToPhysicalType`, **`ipNetToPhysicalState`** ∈ reachable/stale/delay/probe/invalid/unknown/incomplete — the RFC 4861 NUD state machine |
| `IPV6-MIB::ipv6NetToMediaTable` | `ipv6IfIndex, netAddress` | obsolete |
| `openconfig-if-ip` | `ipv4/neighbors/neighbor[ip]`, `ipv6/neighbors/neighbor[ip]` | `state/{link-layer-address, origin, is-router, neighbor-state}` |

`ipNetToPhysicalState` is the interesting column: it is genuinely defined only
for IPv6 ND, and IPv4 implementations map ARP entries onto it approximately.
FlowSeer's `NeighborReachability` rename (from `NeighborState`) is the right
call, and the research doc's restriction of `is_router` to IPv6 rows is exactly
right — there is no IPv4 equivalent.

### Vendor mapping

| Family | Surface |
|---|---|
| IETF | both generations |
| Cisco SMB | `CISCOSB-IPv6::rlipNetToPhysicalTable [AUG ipNetToPhysicalEntry]`, `rlIpNetToPhysicalTableClearTable[ifIndex]` (a clear *operation*) |
| HP ProCurve | `HP-ICF-IPCONFIG::hpicfIpNetToPhysicalTable [AUG]` |
| Huawei | `HUAWEI-ETHARP-MIB::hwEthARPShowWithInterAndVidTable[ifIndex, vid, ipAddr]` — **VLAN in the key**, which the standard table lacks; plus `HUAWEI-ND-MIB` |
| Comware | `HH3C-ARP-ENTRY-MIB` |
| LANCOM SX | `LCOS-SX-MIB::lcsIPStatusNeighborCacheTable[index]` — index-keyed, so rows renumber |
| Cisco IOS-XE | `Cisco-IOS-XE-arp-oper`: `arp-data/arp-vrf[vrf]/arp-entry[address]` — **VRF-scoped**, which the standard MIB is not |

### Traps and pitfalls

- **No VRF dimension in the standard table.** `ipNetToPhysicalTable` is keyed on
  ifIndex+address, and on a VRF-aware device the same address can exist in two
  VRFs on two interfaces — so it works by accident, until the interface is
  shared. Cisco's YANG model adds VRF; the MIB never will. NAPALM's
  `get_arp_table` has the same gap.
- **Huawei adds VLAN to the key** because an ARP entry on a VLANIF interface is
  really per-VLAN. That is more precise than the standard and does not map back.
- Entries age out; the table is a snapshot with no history. Netdisco's
  `node_ip` table with `time_first`/`time_last` is the prior art for turning
  snapshots into an answer to "who had this IP last Tuesday", and again it lives
  above the device model.
- `ipNetToPhysicalPhysAddress` is empty for incomplete entries. Presence
  matters; a zero MAC is not the same as no MAC.

### FlowSeer status

`net/ip/v1/neighbor_entry.proto`, `neighbor_origin.proto`,
`neighbor_reachability.proto` — device-wide table row, as the research doc
specifies. Gaps: no VRF or VLAN dimension, no time axis.

## rib-fib

**What it is.** The routing table. Three generations of MIB, all with problems,
and one modern model that finally separates RIB from FIB.

### Canonical models

| Table | Key | Verdict |
|---|---|---|
| `RFC1213-MIB::ipRouteTable` | `ipRouteDest` | **obsolete**. One route per destination — cannot express ECMP, cannot express two protocols offering the same prefix, no mask in the key so `10.0.0.0/8` and `10.0.0.0/16` collide |
| `IP-FORWARD-MIB::ipForwardTable` (RFC 1354) | `dest, proto, policy, nextHop` | **deprecated**. Adds proto and next-hop to the key so ECMP works; still IPv4-only, and `policy` is a vague TOS-ish integer |
| `IP-FORWARD-MIB::ipCidrRouteTable` (RFC 2096) | `dest, mask, tos, nextHop` | **deprecated**. Mask in the key, so prefixes no longer collide |
| `IP-FORWARD-MIB::inetCidrRouteTable` (RFC 4292) | `destType, dest, pfxLen, policy, nextHopType, nextHop` | current. Family-agnostic, `inetCidrRouteIfIndex`, `inetCidrRouteType` (other/reject/local/remote/blackhole), `inetCidrRouteProto` (an IANA-RTPROTO value), `inetCidrRouteAge`, `inetCidrRouteMetric1..5`, `inetCidrRouteNextHopAS` |
| `openconfig-aft` | `afts/ipv4-unicast/ipv4-entry[prefix]` → `next-hop-group` → `next-hops/next-hop[index]` | the **FIB**, with a proper next-hop-group indirection |
| `openconfig-rib-bgp` | per-AFI RIB tables, adj-rib-in-pre/post, loc-rib, adj-rib-out | the **RIB**, per protocol |
| `openconfig-local-routing` | `static-routes/static[prefix]`, `local-aggregates/aggregate[prefix]` | configured routes only |

**The RIB/FIB distinction is the point.** `inetCidrRouteTable` claims to be the
forwarding table but on most implementations returns selected-RIB entries.
OpenConfig split them deliberately: AFT is what the hardware forwards on, the
RIB models are what each protocol offered. FlowSeer's net-core research says
"selected RIB state must not be conflated with installed FIB state" — the corpus
shows why: there is no MIB that gets this right, so any SNMP-sourced routing
data is ambiguous by construction and must be labelled as such.

### The VRF problem

`inetCidrRouteTable` has **no VRF dimension**. On a VRF-aware device the agent
either exposes only the default VRF, or exposes a per-VRF SNMP context (SNMPv3
contextName, or the `community@vrf` hack on v2c). `MPLS-L3VPN-STD-MIB` adds
`mplsL3VpnVrfRteTable[vrfName, ...]` as a parallel table. FlowSeer's decision to
keep routing out of `net/ip/v1` until a network-instance-aware design exists is
directly supported by this.

### Vendor mapping

| Family | Surface |
|---|---|
| IETF | all four generations, usually two or three present at once |
| Cisco SMB | `rlIpCidrRouteExtTable [AUG ipCidrRouteEntry]`, `rlinetCidrRouteTable [AUG inetCidrRouteEntry]`, `rlInternInetCidrRouteTable[...]` |
| HP ProCurve | `HP-ICF-IP-ROUTING::hpicfIpCidrRouteTable [AUG]`, `hpicfInetCidrRouteTable [AUG]`, `hpicfInetCidrRouteStatsTable[destType]` |
| Comware | `HH3C-UNICAST-MIB` (plus `hh3cURPFTable[ifIndex]`) |
| Huawei | `HUAWEI-RM-EXT-MIB` |
| LANCOM LCOS | `lcsSetupIpRouterIpRoutingTableTable[ipAddress, ipNetmask, rtgTag]` — **`rtgTag` is LCOS's routing-domain dimension**, i.e. LANCOM does have a VRF-equivalent in the key where the standard does not |
| Ruckus ICX / Aruba CX | `openconfig-aft`, `openconfig-local-routing` |

### FlowSeer status

Correctly *absent*. The research doc calls for removing the existing routing
files from `net/ip/v1` before stability and redesigning against a
network-instance-aware slice. The corpus fully supports that; the replacement
design needs (a) a network-instance key, (b) an explicit RIB-vs-FIB
discriminator, and (c) a next-hop-group indirection so ECMP is representable
without row duplication.

## static-route

**What it is.** Operator-configured routes. Separated from the RIB because it is
intent, not observation, and because it is the one part of routing that a switch
without a routing protocol still has.

`openconfig-local-routing::static-routes/static[prefix]` with
`next-hops/next-hop[index]/config/{next-hop, interface-ref, metric, recurse}` is
the clean model.

| Family | Surface | Key shape |
|---|---|---|
| Cisco SMB | `rlIpStaticRouteTable[dest, mask, tos, nextHop]`, `rlInetStaticRouteTable[destType, dest, pfxLen, nextHopType, nextHop, ifIndex]` | full tuple |
| HP ProCurve | `HP-ICF-IP-ROUTING::hpicfIpStaticRouteTable[prefixType, prefix, prefixLength, fwdAddrType, fwdAddr, fwdIfIndex]` plus `hpicfIpStaticRouteBfdTable` (same key) — **static route with BFD tracking** | full tuple |
| Huawei | `HUAWEI-RM-EXT-MIB::hwStaticRouteTable[sourceVpnName, destIp, destMask, destVpnName, nextHop, outIfIndex]` — **two VPN names in the key**, source and destination, for inter-VRF static routes | VRF-aware |
| Ruckus ICX | `FOUNDRY-SN-IP-MIB::snRtIpStaticRouteTable[dest, mask]` — and a second `snRtIpStaticRouteTable[index]` in the HP-SN copy | inconsistent |
| D-Link | `staticRouteTable[ipAddr, netmask, gateway]`, `staticRouteV6Table[...]` (DGS-1210 line) | |
| FASTPATH family | `agentStaticRoutesTable[networkAddress, netMask, nextHop, type, preference]`, `agentIpv6StaticRouteTable[dest, pfxLength, ifIndex, nextHop]` | |
| HP BladeSystem | `ipCurCfgStaticRouteTable[indx]` / `ipNewCfgStaticRouteTable[indx]` — **the current/new config pair**, Blade's whole MIB is built this way | index |

**Huawei's two-VPN key is the one to notice**: it is the only vendor in the
corpus whose static-route model is VRF-complete, and it shows what the standard
model is missing.

The `ipCurCfg*`/`ipNewCfg*` pattern across all HP BladeSystem MIBs is a
candidate/running config split expressed in SNMP — a rare and interesting
answer to the same problem NETCONF solves with datastores.

## vrf

**What it is.** A routing/forwarding instance — VRF, VRF-lite, network
instance, virtual router, virtual system, context, MDC, VS.

### Canonical models

`openconfig-network-instance` is the general form:
`network-instances/network-instance[name]` with `config/type` ∈
`DEFAULT_INSTANCE` | `L3VRF` | `L2VSI` | `L2P2P` | `L2L3`, and everything
protocol-related — `protocols/protocol[identifier,name]`, `tables`, `afts`,
`vlans`, `fdb`, `interfaces` — nested underneath. This is the model FlowSeer's
research doc points at.

`MPLS-L3VPN-STD-MIB` (RFC 4382) is the SNMP answer:
`mplsL3VpnVrfTable[mplsL3VpnVrfName]`, `mplsL3VpnVrfRTTable[vrfName, rtIndex,
rtType]`, `mplsL3VpnIfConfTable[vrfName, ifIndex]`,
`mplsL3VpnVrfRteTable[vrfName, destType, dest, pfxLen, policy, nextHopType,
nextHop]` — a VRF-scoped route table. Also `PPVPN-TC-MIB` / `VPN-TC-STD-MIB` for
the RD/RT types.

### Vendor mapping — and the terminology minefield

| Family | Name | Surface |
|---|---|---|
| D-Link | VRF-Lite | `DLINKSW-VRF-LITE-MIB::dVrfLiteForwardingTable[ifIndex]`, `dVrfLiteImportMapTable[vrfName]`, `dVrfLiteMaxRoutesTable[vrfName]` |
| Comware | Context, MDC | `HH3C-CONTEXT-MIB::hh3cContextControlTable[index]`; `HH3C-MDC-MIB::hh3cMDCControlTable[index]` + per-MDC CPU/memory/disk resource tables — **MDC is device virtualisation, not a VRF**, closer to a virtual chassis |
| Huawei | VPN instance, VS | `HUAWEI-L3VPN-EXT-MIB::hwL3vpnStatisticsTable[vrfIndex]`; `HUAWEI-VS-MIB` (virtual system = device virtualisation) |
| Cisco IOS-XE | VRF | native `vrf` plus `openconfig-network-instance` deviations |
| LANCOM LCOS | routing tag (`rtgTag`) | not a VRF proper — a tag on routes and interfaces that partitions the table |
| MikroTik | VRF | RouterOS `/ip/vrf` |
| Everyone else | absent | most access switches have no VRF |

**Three different ideas share this space:** a routing instance (VRF), a
forwarding domain (L2VSI/bridge domain), and *device* virtualisation (MDC, VS,
Cisco VDC). OpenConfig's network-instance unifies the first two deliberately and
excludes the third. Anyone reading Comware's `HH3C-MDC-MIB` expecting VRFs will
be badly misled.

For FlowSeer this is the missing dimension named in
[03-switching](03-switching.md#the-bridge-domain-problem-once-up-front) and in
the net-core research. The recommendation is the same in both places: adopt the
network-instance concept, default it explicitly, and thread it through FDB,
VLAN, route, and neighbour keys before those messages stabilise.

## vrrp

**What it is.** First-hop gateway redundancy: several routers share a virtual IP
and MAC, one is master.

### Canonical models

| Model | Key |
|---|---|
| `VRRP-MIB` (RFC 2787) | `vrrpOperTable[ifIndex, vrrpOperVrId]` — VRRPv2, IPv4 only. `vrrpOperVirtualMacAddr`, `vrrpOperState` (initialize/backup/master), `vrrpOperPriority`, `vrrpOperMasterIpAddr`; `vrrpAssoIpAddrTable[ifIndex, vrId, addr]`; `vrrpRouterStatsTable` |
| `VRRPV3-MIB` (RFC 6527) | `vrrpv3OperationsTable[inetAddrType, vrId, ifIndex]` — note the **address type first in the key**, so v4 and v6 groups coexist |
| `openconfig-if-ip` | `ipv4/addresses/address/vrrp/vrrp-group[virtual-router-id]` — **hung off the address, not the interface**, plus `interface-tracking` |

### Vendor mapping

| Family | Surface |
|---|---|
| IETF | both |
| Cisco SMB | `CISCOSB-VRRP::rlVrrpv3OperationsTable [AUG]`, `rlVrrpv3AssociatedIpAddrTable [AUG]`, `rlVrrpv3CountersTable[ifIndex]` |
| HP ProCurve | `HP-ICF-VRRP-MIB::hpicfVrrpOperTable [AUG vrrpOperEntry]`, `hpicfVrrpTrackTable[ifIndex, vrId, trackType, trackEntity]` — **object tracking**, which the standard lacks; also `HP-ICF-XRRP` (HP's own) and `HP-SN-VSRP-MIB` (Foundry's) |
| FASTPATH family | `agentRouterVrrpOperTable[ifIndex, vrId]`, `agentRouterVrrpTrackIntfTable[ifIndex, vrId, trackIntf]`, `agentRouterVrrpTrackRouteTable[ifIndex, vrId, prefix, pfxLen]` — interface *and* route tracking |
| D-Link | `DLINKSW-VRRP-EXT-MIB::dVrrpCriticalIpTable[ifIndex, vrId]` |
| Comware | `HH3C-VRRP-EXT-MIB::hh3cVrrpExtTable[ifIndex, vrId, trackInterface]` |
| Huawei | `HUAWEI-VRRP-EXT-MIB`; plus `HUAWEI-VGMP-MIB` (VRRP group management for firewalls) and `HUAWEI-E-TRUNK-MIB` |
| Ruckus ICX | `FOUNDRY-SN-IP-VRRP-MIB::snVrrpVirRtrTable[port, vrId]` and `snVrrpVirRtr2Table[ifIndex, vrId]` — **two generations, the `2` one ifIndex-keyed**; plus `FOUNDRY-SN-VSRP-MIB` (VSRP, Foundry's L2+L3 variant) |
| Cisco IOS-XE | `Cisco-IOS-XE-hsrp-oper` — **HSRP**, Cisco's proprietary predecessor, still dominant on Cisco networks. `hsrp-oper-data/hsrp-group-info[group-id]`, `hsrp-neighbor`, plus `Cisco-IOS-XE-hsrp-events` |
| Aruba wireless | `WLSX-HA-MIB` — controller HA, a different mechanism with the same purpose |

### Notes

The **tracking** extension is present in five vendors and absent from both
standards. It is also the operationally important part: a VRRP master that has
not failed over because its uplink track is misconfigured is a common outage.

GLBP, HSRP, VSRP, XRRP, VGMP are all the same entity with different protocols.
As with [udld](02-interface.md#udld), one entity with a protocol discriminator
beats five packages.

## nat

**What it is.** Address and port translation.

Standard: `NAT-MIB` (RFC 4008) — not present in this corpus at all, which is
itself informative. `openconfig-nat` exists upstream but is not in the vendored
OpenConfig set.

| Family | Surface |
|---|---|
| Comware | `HH3C-NAT-MIB`: `hh3cNATPoolInfoTable[poolIdx]`, `hh3cNATOutboundTable[ifIndex, aclNo]`, `hh3cNATServerTable[ifIndex, protoType, globalIP, startGlobalPort, vpnIndex]`, `hh3cNATTimeOutTable[protocol]` |
| Huawei | `HUAWEI-NAT-MIB::hwNatAddressGroupInfoTable[index]`, `hwNatInternalServerTable[serverIndex]`; `HUAWEI-NAT-EUDM-MIB` for the carrier-grade version |
| MikroTik | RouterOS `/ip/firewall/nat` over REST — the practical surface |
| LANCOM LCOS | in the firewall/masquerading tree |
| Switches | none — NAT is a router/firewall function |

Out of scope for FlowSeer's switch and AP focus; in scope the moment a LANCOM
or MikroTik router is managed as a Device.

## routing-policy

**What it is.** Route maps, prefix lists, redistribution rules, and
policy-based routing.

`openconfig-routing-policy` + `openconfig-defined-sets` is the general model:
`defined-sets/{prefix-sets, neighbor-sets, tag-sets}`,
`policy-definitions/policy-definition[name]/statements/statement[name]/
{conditions, actions}`. `openconfig-bgp-policy` adds BGP-specific condition
sets, and `openconfig-policy-forwarding` + `openconfig-aft-pf` cover PBR.

| Family | Surface |
|---|---|
| Cisco SMB | `CISCOSB-ROUTEMAP-MIB`, `CISCOSB-PBR-MIB::rlPBRTable[ifIndex, inetType]` + `rlRouteMapPbrTable[mapName, sectionId, inetType]`, `CISCOSB-Redistribute::rlRedistTable[dstProto, srcProto, dstProcId, srcProcId, matchType, routeMapName]`, `CISCOSB-ippreflist-MIB` |
| Comware | `HH3C-PBR-MIB`: `hh3cPBRMibPolicyNodeTable[addrType, policyName, nodeId]`, `hh3cPBRMibIfPolicyTable[addrType, ifIndex]`, `hh3cPBRMibMatchAclTable`, `hh3cPBRMibApplyPrecedenceTable` — a proper match/action node model |
| D-Link | `DLINKSW-PBR-MIB`, `DLINKSW-ROUTE-MAP-MIB`, `DLINKSW-IP-ROUTING-MIB::dIpRoutingRoutePolicyTable[index]` + `dIpRoutingPrefixListTable[addrType, name, seqNum]`, plus per-protocol redistribute tables |
| Foundry lineage (Ruckus ICX, HP ProCurve) | `snBgp4RouteMapFilterTable[mapName, seqNum]` + `snBgp4RouteMapMatchTable` + `snBgp4RouteMapSetTable` — the classic filter/match/set triple |
| FASTPATH family | `FASTPATH-ROUTE-POLICY-MIB::fastpathRoutePolicyNameTable[name, actionType, sequence]`, `fastpathRoutePolicyStamentTable[stmtName, seqNum, action]` (sic — the typo is upstream), `fastpathRoutePolicyIfTable[ifIndex, name]` |
| LANCOM LCOS | `lcsSetupRoutProtFilterPrefixListTable[name, ipAddress]` |

**The universal shape is match/action statements in a named, sequenced list.**
Every vendor has it and every vendor keys it slightly differently. It maps
cleanly onto FlowSeer's `net/packet/v1` match atoms, and it is the first real
consumer for them — the net-core research deferred a monolithic packet matcher
"until its first real consumer", and routing policy plus [ACLs](06-qos.md#acl)
are that consumer.

## dhcp

**What it is.** Four distinct roles that share a name: client, server, relay,
and snooping. 851 matched tables, second only to LLDP.

| Role | What it observes |
|---|---|
| **Client** | the device's own lease — address, server, lease time, options received |
| **Server** | pools, ranges, static bindings, active leases, options served |
| **Relay** | which servers a VLAN/interface forwards to, Option 82 policy |
| **Snooping** | the binding table (MAC ↔ IP ↔ VLAN ↔ port) learned by watching DHCP, plus trusted ports |

**Snooping is the interesting one for FlowSeer** because the binding table is a
better endpoint-location source than FDB+ARP joined: it has MAC, IP, VLAN, port,
and a lease time, all in one row, all learned rather than inferred. It also
feeds [l2-security-guard](#l2-security-guard).

### Canonical models

No standard SNMP MIB for any of the four (`DHCP-MIB` drafts never landed).
`ietf-dhcpv6-*` and `openconfig-relay-agent` exist in YANG;
`openconfig-relay-agent` is not in the vendored set.

## dns

Thin and mostly uninteresting: a resolver configuration (server list, search
domains) and a static host table.

Standards: `DNS-RESOLVER-MIB` and `DNS-SERVER-MIB` (RFC 1612/1611, historic and
essentially unimplemented — they are present in the corpus but nothing populates
them). `openconfig-system` `dns` with `servers/server[address]`,
`host-entries/host-entry[hostname]`, and `search` is the practical model, and
Aruba CX and Ruckus ICX both expose it.

Vendor tables of note: `CISCOSB-DNSCL-MIB::rlDnsClv2ServersTable[source,
ifIndex, preference, addrType, inetAddr, subTree, class]` — a **per-subtree,
per-source, preference-ordered** resolver config, which is far more expressive
than anyone needs and shows Cisco SMB's habit of putting policy in keys;
`DLINKSW-DNS-MIB` splits static and dynamic name servers and hosts into four
tables; FASTPATH's `FASTPATH-DNS-RESOLVER-CONTROL-MIB` is the shared clone.

Value to FlowSeer: low, except that the resolver list is useful device
context when diagnosing management-plane reachability.

## ip-diagnostics

**What it is.** On-demand and scheduled reachability tests run *by* the device —
ping, traceroute, and the SLA/performance frameworks built on them.

### Canonical models

`DISMAN-PING-MIB` and `DISMAN-TRACEROUTE-MIB` (RFC 4560) are real standards with
real adoption, and they have the shape [cable-diag](02-interface.md#cable-diag)
and [config-file](01-platform.md#config-file) also wanted:

- `pingCtlTable[pingCtlOwnerIndex, pingCtlTestName]` — the *test definition*
  (target, probe count, size, timeout, frequency, trap generation).
- `pingResultsTable[same key]` — the aggregate result.
- `pingProbeHistoryTable[same key, probeIndex]` — individual probes.
- Same triple for traceroute, plus `traceRouteHopsTable`.

An owner-plus-name key, a definition table, a results table, and a history
table. **This is the canonical SNMP shape for "a long-running operation with
results", and it is worth adopting as FlowSeer's operation pattern** rather than
inventing one.

### Vendor mapping

| Family | Surface |
|---|---|
| IETF | `DISMAN-PING-MIB`, `DISMAN-TRACEROUTE-MIB` |
| Comware | `HH3C-NQA-MIB::hh3cNqaCtlTable [AUGMENTS pingCtlEntry]` — augments the standard rather than replacing it, plus `hh3cNqaResultsTable` and `hh3cNqaJitterStatsTable`; also `HH3C-TWAMP-MIB` |
| Huawei | `HUAWEI-DISMAN-PING-MIB::hwPingCtlTable [AUG pingCtlEntry]`, `HUAWEI-CE-PING-MIB::hwCePingTable[index]` + result + history (a second, non-standard triple), `NQA-MIB`, `HUAWEI-IPFPM-MIB`, `HUAWEI-IFIT-MIB` (in-band flow telemetry) |
| Cisco SMB | `CISCOSB-IP-SLA::rlSLAOperTable[operId]`, `rlSLATrackTable[trackObj]` — SLA plus **object tracking**, which links to VRRP tracking |
| Cisco IOS-XE | `Cisco-IOS-XE-ip-sla-*` — per-operation-type oper data (dhcp, dns, ftp, http, icmp, jitter, …) |
| Ruckus ICX | `openconfig-probes` — `test-target/target`, `probe-test-state-history-item` |
| LANCOM LCOS | `lcsSetupSlaMonitorIcmpTable[name]`, `lcsStatusSlaMonitorIcmpLastResultTable[name]`, `lcsStatusSlaMonitorIcmpHistoryLogTable[index]` |
| FASTPATH family | DISMAN unmodified |

Comware's and Huawei's `AUGMENTS pingCtlEntry` is a good sign: two large vendors
chose to extend the standard rather than fork it, which is rare in this corpus.

## l2-security-guard

**What it is.** First-hop security: stopping a host from claiming an address or
identity it does not own. Six related mechanisms.

| Mechanism | What it does | Depends on |
|---|---|---|
| DHCP snooping | builds the trusted MAC/IP/VLAN/port binding table | — |
| IP Source Guard | drops traffic whose source IP/MAC is not in the binding | DHCP snooping |
| Dynamic ARP Inspection | drops ARP that contradicts the binding | DHCP snooping |
| IPv6 RA Guard | drops router advertisements from non-router ports | — |
| IPv6 ND Inspection / SAVI | the IPv6 equivalent of DAI, RFC 7039 source-address validation | ND snooping |
| uRPF | drops packets whose source is not routable back out the ingress interface | FIB |

The dependency chain matters: everything except RA Guard and uRPF is downstream
of the snooping binding table, so the binding table is the entity and the rest
are policies applied to it.

| Family | Surface |
|---|---|
| Cisco SMB | `CISCOSB-BRIDGE-SECURITY`: `rlIpSourceGuardPortTable[ifIndex]`, `rlIpSourceGuardTable[ifIndex, ipAddress, vlanTag]`, `rlIpArpInspectListTable[listName, ipAddress]`; `CISCOSB-IPV6FHS-MIB` (IPv6 first-hop security) |
| D-Link | `DLINKSW-DAI-MIB`, `DLINKSW-IP-SOURCE-GUARD-MIB`, `DLINKSW-RA-GUARD-MIB`, `DLINKSW-ND-INSPECT-MIB`, `DLINKSW-IPV6-SNOOPING-MIB`, `DLINKSW-IPV6-SRC-GUARD-MIB`, `DLINKSW-URPF-MIB`, `DLINKSW-IMPB-MIB` (IP-MAC-Port Binding: `impbWhiteListTable[ip, mac]`, `impbBlackListTable[mac, vlanId, port]`, `impbSmartTable[mac, port, ip]`) — **eight MIBs, the most complete first-hop-security surface in the corpus** |
| HP ProCurve | `HP-ICF-ARP-PROTECT::hpicfArpProtectPortTable[ifIndex]`, `hpicfArpProtectVlanStatTable[index]` |
| Comware | `HH3C-ARP-RATELIMIT-MIB`, `HH3C-ARP-SOURCE-SUPPRESSION-MIB`, `HH3C-SAVA-MIB`, `HH3C-DOT11-SAVI-MIB` (SAVI on wireless) |
| Huawei | `HUAWEI-MFF-MIB` (MAC-forced forwarding), `HUAWEI-SECURITY-MIB`, uRPF inside `HUAWEI-CBQOS-MIB` |
| LANCOM SX | `gs2310IPSourceGuardPortConfigTable[Port]`, `gs2310IPSourceGuardStaticTable[index]`, `gs2310IPSourceGuardDynamicTable[index]`, `gs2310ARPInspectionConfTable[portIndex]` |
| Cisco IOS-XE | `Cisco-IOS-XE-ipv6` `source-guard`, `Cisco-IOS-XE-nd` `raguard` |

D-Link's IMPB white/black/smart list trio is worth noting as a data source: it
is effectively a curated endpoint inventory with an enforcement action attached.

## icmp-tcp-udp

**What it is.** Host-stack statistics and open connections on the device itself.

`IP-MIB::icmpStatsTable[icmpStatsIPVersion]` and
`icmpMsgStatsTable[icmpStatsIPVersion, icmpMsgStatsType]` (RFC 4293 — per ICMP
type, both families); `TCP-MIB::tcpConnectionTable` /
`tcpListenerTable` (RFC 4022) and `UDP-MIB::udpEndpointTable` (RFC 4113); the
obsolete `IPV6-TCP-MIB` / `IPV6-UDP-MIB` / `IPV6-ICMP-MIB`.

Vendor extras: `CISCOSB-TCPSESSIONS::rlTcpSessionTable[localAddrType,
localAddress, localPort, remAddrType, remAddress, remPort]` and
`CISCOSB-SOCKET-MIB::rlSocketTable[socketId]` — an open-connection list on a
switch, useful for spotting unexpected management sessions;
`HP-ICF-RATE-LIMIT-MIB::hpICMPRateLimitPortConfigTable[index]`;
Huawei's `HUAWEI-ATK-MIB` / `-ATK-EUDM-MIB` attack-detection tables keyed on
`[mplsVpnVrfName, floodIP]`.

Relevance to FlowSeer: low as telemetry, moderate as a security signal (open
listeners on a switch, ICMP flood counters). Note that FlowSeer's
`net/packet/v1` already models ICMPv4/ICMPv6 type/code numerically, which is the
right representation for both this entity and ACL matching.
