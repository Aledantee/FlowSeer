# MikroTik RouterOS / SwOS

Every claim carries a source link. Where documentation is contradictory or version-dependent,
say which version the claim holds for.

## What it manages

MikroTik ships two firmware families on overlapping hardware. RouterOS runs on routers, the
CCR/RB lines, and (optionally) the CRS/CSS switch-on-chip boards; it is a full router OS with
Layer 3 routing, firewall, wireless, and a switch chip driver underneath. SwOS and SwOS Lite are
switch-only firmware for the CSS/CRS lines: no routing, no scripting, configured only over a
web browser [8]. Several CRS/CSS models can dual-boot between RouterOS and SwOS; the choice is a
RouterBOARD setting (`/system routerboard settings set boot-os=swos`) or a boot-time button press,
not a live mode switch [10].

There is no cloud controller tier comparable to Meraki or Aruba Central. MikroTik's own
central-management story is on-box or on-prem: CAPsMAN (wireless AP controller, runs as a
RouterOS service on one router) and The Dude (monitoring/mapping tool, runs as a RouterOS package
or a separate Windows/macOS app) [12][13]. IP Cloud's core function is DDNS, but it also bundles
time sync, encrypted backup storage, a "Back to Home" remote-access relay, and file share; none of
these is a device configuration/management API — see "Provisioning and onboarding" below [18].

Scale limits are not published in the docs consulted; CAPsMAN documentation states support for an
unspecified but large number of CAPs ("no hard limit is documented" — unverified, from secondary
source only) [13].

## Authentication and authorisation

RouterOS uses a single flat user/group model shared by every management surface (REST, binary
API, SSH, Winbox, SNMP-write) — there is no separate API-key or OAuth layer. A router's local
users, or a RADIUS backend if configured, authenticate every surface [5].

- **REST API**: HTTP Basic Auth against RouterOS console credentials. MikroTik recommends
  `www-ssl` (HTTPS); the equivalent plain-HTTP service `www`, available from RouterOS v7.9,
  exposes the password in cleartext and is not recommended [1].
- **Binary API**: since RouterOS v6.43 the login sentence carries the username and password in
  plaintext over the (ideally TLS, port 8729) connection; the older MD5-challenge login flow from
  pre-6.43 releases still works for backward compatibility but is deprecated [3].
- **SSH**: standard SSH auth (password or public key) against the same user database.
- **SNMP**: v1/v2c use a cleartext community string, optionally restricted by source address.
  v3 has three security levels — `none` (noAuthNoPriv), `authorized` (authNoPriv), `private`
  (authPriv) — with MD5 or SHA1 for authentication and DES or AES (AES since RouterOS v6.16) for
  privacy, both requiring 8+ character passwords [6].
- **SwOS**: a single admin account (default `admin`, no password) authenticated with HTTP Digest;
  SwOS Lite is documented to serve over plain HTTP with Digest auth and no HTTPS option
  (unverified: not confirmed against a MikroTik doc page, only community/forum sources) [9]. The
  lab dossier at `docs/research/device-inventory/lab/labsw02-mikrotik-css326.md` documents the
  `.b` endpoints observed live against a CSS326 running SwOS; treat that capture as the source of
  record over the `.b` endpoint names listed here once it lands.

There is no scoped, read-only API role comparable to a controller's "viewer" role. A least-
privilege read-only integration is built by creating a RouterOS user in a group with only `read`
and `api`/`rest-api`/`ssh` policy bits (not `write`, `policy`, `sensitive`, or `test`); RouterOS
group policies are documented under user management but were not fetched for this brief.
A write integration needs `write` plus the relevant service policy bit and, for anything touching
firewall or routing, `sensitive`.

## Data model

RouterOS has no organisation hierarchy — every device is configured and queried independently.
There is no fleet-level identity API; a device's stable identifiers are its serial number and
board MAC/identity, both readable at `/system resource` and `/system routerboard` over REST, the
binary API, or SNMP (`mtxrSystem` scalars) [4].

- **Inventory read**: REST `GET /rest/<console-path>` mirrors the console menu tree one-for-one
  (`/rest/interface/ethernet`, `/rest/ip/address`, `/rest/system/resource`, …) [1]. Filtering is by
  query string matching property names (`?network=10.155.101.0&dynamic=true`); returned fields can
  be restricted with a `.proplist` parameter. There is no cursor-based pagination — a `GET` returns
  the full result set for the query given, and MikroTik enforces a 60-second execution timeout on
  requests that would otherwise run indefinitely (e.g. a `ping` without a `count`), so long-running
  commands need explicit limiting parameters [1].
- **Configuration model**: imperative, not declarative. `PUT` adds a record (console `add`),
  `PATCH` modifies one (console `set`), `DELETE` removes one (console `remove`), `GET` lists
  (console `print`); `POST` invokes arbitrary console commands including non-CRUD ones (`/beep`,
  `/system reboot`) [1]. Every REST response returns all values as JSON strings, even numeric and
  boolean fields, and request bodies accept RouterOS's `0x`/octal numeric literals [1].
- **`.id` field**: every list-backed console item carries an internal identifier of the form `*1`,
  `*2`, `*A`, exposed as `.id` over REST and as `=.id=` over the binary API. It is RouterOS's
  internal row pointer, **not stable across reboots**; both the console docs and the vendored
  network-domain-atlas dossier warn against keying on it, using the item's named field (`name`,
  `address`, `interface`) instead where one exists [7][1].
- **No candidate/commit**: RouterOS applies every `set`/`add`/`remove` (and REST `PATCH`/`PUT`/
  `DELETE`) immediately to the running configuration. There is no staged or candidate
  configuration and no atomic multi-object commit. The only safety net is Safe Mode (`F4`/`Ctrl+X`
  in the console, or the binary API's safe-mode commands), which rolls back everything done in the
  session if the session ends abnormally before an explicit confirm — a session-scoped undo, not a
  config-versioning system [7].
- **Read-after-write**: not documented as eventually consistent; RouterOS is a single control
  point per device, so a `GET` after a `PATCH`/`PUT` reflects the change immediately on that
  device. There is no fleet propagation delay because there is no fleet controller — CAPsMAN
  pushes to CAPs on its own schedule, which is a separate concern from device-local REST/API
  writes.

## Telemetry and events

- **Polling**: the console/REST tree carries live counters under the same paths as configuration
  (`/interface/ethernet/monitor`, `/system/resource`, `/system/health`), so telemetry and config
  share one surface and one auth model. SNMP is the alternative poll surface via
  `MIKROTIK-MIB`'s `mtxrInterfaceStatsTable`, `mtxrGaugeTable` (voltage/temperature/fan), and
  `mtxrOpticalTable` (transceiver DOM) [4].
- **Push over the binary API**: the `/listen` command (documented informally as "listen") turns a
  print-type command into a subscription — RouterOS emits `!re` sentences as matching items
  change, and marks a removed item with `=.dead=yes` in its final sentence. The subscription runs
  until the client sends `/cancel` for that tag [3]. This is the only native streaming mechanism;
  REST has no equivalent and a REST client has to poll.
- **SNMP traps**: RouterOS can send SNMPv1/v2c/v3 traps for interface state changes and service
  startup events; the exact trap OID list is defined in `MIKROTIK-MIB`'s `mtxrTraps` branch [4][6].
- No webhook or syslog-as-JSON push mechanism is documented for RouterOS; syslog output exists
  (standard RFC 3164/5424-shaped) but was out of scope for this fetch.

## Rate limits, quotas, pagination

No published numeric rate limit for the REST API, the binary API, or SSH. The one documented
constraint is the REST API's 60-second execution timeout per request for indefinite/streaming-style
commands, worked around with `once` or count/duration-limiting parameters [1]. No pagination
parameter exists on REST `GET`; a query returns everything matching the filter in one response.
MikroTik gives no backoff guidance because there is no rate limiting to back off from — the
practical constraint is the device's own CPU budget under concurrent management sessions, which
the docs consulted do not quantify.

## Device-side protocols still available

There is no controller layer that locks out device-local protocols on RouterOS — REST, the binary
API, SSH, Winbox, and SNMP are independent services that can all be enabled simultaneously, each
toggled under `/ip service` (REST/SSH/Winbox) or `/snmp` [1][6]. Factory defaults enable `ftp`,
`ssh`, `telnet`, `www` (plain-HTTP REST, port 80), `api` (binary API, port 8728), `api-ssl`
(port 8729), and `winbox`; only `www-ssl` (HTTPS REST) and SNMP are off by default and must be
turned on explicitly [19][4]. The binary API and plain-HTTP REST are therefore both reachable out
of the box, not gated behind an explicit enable step the way `www-ssl` and SNMP are.

- **No NETCONF, RESTCONF, or gNMI.** No YANG models exist for RouterOS; this was already recorded
  in `spec/openapi/mikrotik/SOURCES.md` and confirmed by the absence of any such surface in the
  docs fetched for this brief.
- **SwOS** has no CLI, no API, and no SSH — the vendor docs state plainly that "console access,
  API, or other management interfaces are not supported," leaving only the HTTP web UI (with its
  undocumented internal `.b` endpoints) and read-only SNMP v1/v2c [8].

## Provisioning and onboarding

RouterOS has no fleet-adoption workflow (no claim-by-serial, no ZTP registration to a cloud
account). A new device is reachable over Winbox/WebFig on its default IP or via MNDP-based
discovery from another MikroTik device on the same L2 segment, then configured directly. IP Cloud
(see below) offers a DDNS hostname but does not gate or register the device anywhere.

**Netinstall** is MikroTik's recovery/reimage tool (Windows GUI and Linux CLI): it PXE/TFTP-boots
the target into a minimal Etherboot loader and pushes a RouterOS package over the network,
re-formatting the system drive. It preserves the RouterOS license key and RouterBOOT settings but
erases all configuration; it requires exactly one active network interface on the controlling
computer during the process [15].

Firmware/package management on a running device is done via `/system package` (installed
packages) and `/system routerboard upgrade` (bootloader firmware), both reachable over REST, the
binary API, and SSH — no separate firmware-push channel exists outside those surfaces.

## Known quirks and traps

- **`.id` is not a stable identifier.** It is reassigned across reboots on some item types; use
  the named field instead [7].
- **Three menus, one conceptual interface.** `/interface/ethernet` (the physical port),
  `/interface/bridge/port` (bridge membership), and `/interface/vlan` (a tagged sub-interface) are
  separate console/REST trees describing one physical interface's different facets — a naive
  "interface" model that maps 1:1 to a REST path will miss two of the three [7].
- **Bridge/VLAN configuration has no SNMP representation at all.** The community MIB covers
  interface counters, optics, PoE, and wireless, but MikroTik's bridge-VLAN model (the thing that
  determines L2 behavior on a CRS switch) exists only in the REST/console tree [7].
- **Two mutually exclusive wireless stacks.** `MIKROTIK-MIB` carries both the legacy `mtxrWl*`
  tables (old `/interface wireless` package) and the new `mtxrWifi*` tables (`/interface wifi`,
  "wifiwave2"); a given device populates only one set depending on RouterOS version and hardware,
  and there is no MIB field that tells you which without probing both [7].
- **The community OpenAPI document is a map of calls, not of responses.** Endpoint and parameter
  *names* are reliable because they come straight from `/console/inspect`; parameter *types* are
  frequently the JSON schema `any`, and there are no field descriptions. Treat every REST response
  as untyped JSON and validate at the decoder, not against the schema [2].
- **Everything is a JSON string over REST**, including numbers and booleans — a naive decoder
  that expects `true`/`false` or a JSON number will need explicit coercion [1].
- **Export omits secrets by default.** `/export` does not include user passwords, installed
  certificates, SSH keys, or the Dude/User-manager databases unless `show-sensitive` is given; an
  export-based backup strategy that assumes completeness will silently lose credential material
  [14].
- **No candidate/commit anywhere in the stack.** Every write surface (REST `PATCH`/`PUT`/`DELETE`,
  binary API `set`/`add`/`remove`, SSH console, SNMP `SET` on writable OIDs) applies immediately.
  The only rollback mechanism is session-scoped Safe Mode, not a queued/reviewable change set [7].
- **SwOS and RouterOS are exclusive per boot, not concurrent.** A CRS/CSS dual-boot device runs
  one firmware at a time; switching requires a reboot into the other OS, so an integration cannot
  assume a fixed protocol surface for a device model without first checking its current boot mode
  [10].

## What FlowSeer needs

- **Credentials to store**: one set of RouterOS username/password (or RADIUS-backed credential)
  per device for REST/binary-API/SSH, since all three share the same user database; a separate
  SNMPv3 user/auth/priv triple if FlowSeer also polls SNMP; a separate SwOS admin credential (HTTP
  Digest) for any CSS/CRS device running SwOS instead of RouterOS.
- **Inventory**: REST `GET /rest/system/resource`, `/rest/system/routerboard`,
  `/rest/interface/ethernet`, `/rest/ip/address` for RouterOS devices; SNMP walk of `mtxrSystem`
  and `IF-MIB`/`mtxrInterfaceStatsTable` as a fallback or for SwOS-mode switches (SwOS has no REST
  API at all — SNMP read-only is the only machine-readable surface there) [8][4].
- **Configuration**: REST `PATCH`/`PUT`/`DELETE` against the console-mirrored paths; there is no
  declarative apply, so FlowSeer has to compute the imperative diff itself (which records to add,
  set, or remove) rather than pushing a full desired-state document.
- **Telemetry**: poll REST/SNMP counters on an interval FlowSeer controls, since RouterOS gives no
  webhook push; use the binary API's `/listen` mechanism only if a persistent long-lived
  connection per device is acceptable, since REST cannot stream.
- **Identifiers to key on**: RouterOS `/system routerboard` serial number as the stable device
  identity; named fields (`name`, `default-name`, `address`) as the row key within a device, never
  `.id`.
- **Rate-limit budget**: none published; budget for the REST API's 60-second per-request execution
  ceiling and design polling to avoid unbounded commands.
- **Minimum API version to target**: RouterOS v7.1beta4 is the first release with the REST API at
  all [1]; the vendored OpenAPI document is generated against v7.24, so anything targeting the REST
  path list should assume v7.24-shaped paths and verify against older v7.x devices individually,
  since the schema is auto-derived per-version and not published for other versions in this repo.
