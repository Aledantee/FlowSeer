## 2. Standards facts

**MAC randomization / IEEE 802c SLAP (secondary source: `draft-ietf-dhc-slap-quadrant-12` §2, quoting 802c's bit layout):**
- First octet of any IEEE 802 MAC address, from LSB: bit 0 = **M bit** (Individual/Group, i.e. unicast/multicast), bit 1 = **X bit**, "also referred to as the U/L (Universal/Local) bit" — 0 = universally administered (IEEE-assigned OUI), 1 = locally administered.
- For a locally administered address (X/U-L bit = 1), bits 2-3 of the first octet are the **Y bit** and **Z bit**, and together they select one of four **SLAP quadrants**:
  - `Y=1,Z=1` → **SAI** (Standard Assigned Identifier) — assigned by a protocol specified in an IEEE 802 standard.
  - `Y=0,Z=1` → **ELI** (Extended Local Identifier) — assigned from a 24-bit Company ID (CID) issued by the IEEE RA, structurally a locally-administered analogue of an OUI.
  - `Y=0,Z=0` → **AAI** (Administratively Assigned Identifier) — assigned locally by an administrator (this is the quadrant OS-level MAC randomization uses).
  - `Y=1,Z=0` → **Reserved** for future use.
- Practical consequence for client identity: **any client MAC with the U/L bit set is not a stable, vendor-traceable identity** — its OUI lookup is meaningless (it was never IEEE-assigned) and, in the AAI quadrant specifically, the OS may re-roll it per network, per boot, or on a timer.

**MAC randomization per OS (from the prior survey, `docs/research/network-domain-atlas/entities/08-wireless.md` L230-234, unverified beyond that doc's own citation trail — flagged, not re-verified against Apple/Google docs this session):** "MAC randomisation has broken MAC-as-identity for client tracking since iOS 14 / Android 10." iOS and Android both default to a *per-SSID* randomized MAC (a different locally-administered MAC for each network the device joins, stable while joined to that network, unless the user or a rotation policy resets it); this is exactly what makes MAC alone insufficient as a cross-session, cross-network client identity, and why "randomized MAC" is a per-attachment property (which SSID, which epoch) rather than a device-wide constant.

**DHCP fingerprinting options (RFC 2132, primary source):**
- **Option 12 — Host Name** (§3.14): code 12, `Code | Len | Host Name (n octets)`. "This option specifies the name of the client. The name may or may not be qualified with the local domain name."
- **Option 55 — Parameter Request List** (§9.8): code 55, `Code | Len | Option Codes (n octets)`. Client-supplied ordered list of DHCP option codes it wants back; the list itself (its exact ordering and membership) is a widely used passive OS/stack fingerprint (this specific fingerprinting use is standard industry practice, not stated in the RFC itself — RFC 2132 defines only the wire format).
- **Option 60 — Vendor class identifier** (§9.13): code 60, `Code | Len | Vendor class Identifier (n octets)`. Free-form vendor/product string a client may send; used for both DHCP option-class matching server-side and passive device-fingerprinting client-side.
- **Option 81 — Client FQDN** (RFC 4702, primary source): code 81, `Code | Len | Flags | RCODE1 | RCODE2 | Domain Name`. Flags carry the **S bit** (server should/should-not perform the A-record update), **O bit** (server overrode the client's S preference), **N bit** (server should not do any DNS update at all). This is the modern replacement/superset of option 12 for FQDN exchange and DNS-update delegation.

**802.1X session identity (`spec/mib/ieee/IEEE8021-PAE-MIB`, primary vendored source, lines 1116-1180):**
- `dot1xAuthSessionId` (SnmpAdminString, read-only) — "a unique identifier for the session" (802.1X-2001/2004 §9.4.4).
- `dot1xAuthSessionUserName` (SnmpAdminString, read-only) — "the User-Name representing the identity of the Supplicant PAE" (§9.4.4).
- `dot1xAuthSessionAuthenticMethod`, `dot1xAuthSessionTime`, `dot1xAuthSessionTerminateCause` (enumerated: `supplicantLogoff(1)`, `portFailure(2)`, `supplicantRestart(3)`, `reauthFailed(4)`, `authControlForceUnauth(5)`, `portReInit(6)`, `portAdminDisabled(7)`, `notTerminatedYet(999)`), `dot1xAuthSessionFramesRx/Tx` complete the session-stats row. This table is the **wired 802.1X identity source**; RADIUS `User-Name` at the AAA layer is the equivalent value carried over the wire, this MIB is where a switch/controller exposes it locally.

**IEEE802dot11-MIB station identity (`spec/mib/ieee/IEEE802dot11-MIB`, primary vendored source, line 152-209):**
- `dot11StationConfigTable` is `INDEX { ifIndex }` — i.e. the legacy standard models the *local* radio's own station config (its own MAC, `dot11StationID`), not a table of *associated peer* stations. There is no standard MIB table of associated client MACs for a standalone AP in this corpus; `CAPWAP-BASE-MIB::capwapBaseStationTable[wtpCurrId, radioId, stationId]` is the IETF controller-side table that does this (cited from the atlas doc, not re-walked this session).

**Ruckus wireless client (`spec/proto/ruckus/ap/ap_client.proto`, `APClientInfo`, since 3.5, primary vendored source):** `clientMac` (required), `ipAddress`, `ipv6Address`, `wlanId` (int32), `rssi` (int32), `receiveSignalStrength` (int32, distinct from rssi — "last recorded signal strength received"), `noiseFloor` (int32), `vlan` (int32), `rxFrames`/`rxBytes`/`txFrames`/`txBytes` (uint64 deltas), `txMgmtFrames`/`rxMgmtFrames`, `throughputEst`, `txDropDataFrames`/`txDropMgmtFrames`, `rxCRCErrFrames`, `txRetry`, `osType` (string, e.g. "Windows 7/Vista, Android" per the field's own doc comment), `radio` (nested `APClientRadio` — band/rate/etc.), `cpeMac` (MAC of a client *behind* this client, i.e. a CPE relay — layered client), `deviceType` (int32, enumerated in `ap_common.proto`, not read this session), `osVendorType` (int32), `modelName` (string), `hostname` (string, added 5.2), `stickyWeak` (uint32 flag for "sticky/weak client" — a roaming-health classification).

**Ruckus wired client (`spec/proto/ruckus/ap/ap_wired_client.proto`, `APWiredClientInfo`, since 3.5.1):** `clientMac`, `ipAddress`, `ipv6Address`, `vlan`, `rxFrames/rxBytes/rxUcast/rxMcast/rxBcast/rxDrop/rxEapol`, `txFrames/txBytes/txUcast/txMcast/txBcast/txDrop/txEapol` (note: **802.1X `Eapol` frame counters exist on the wired-client counters, not a separate table** — Ruckus counts EAPOL traffic per client), `authStatus` (enum `UNAUTH(0)`/`AUTHENTICATED(1)`), `ethIF` (string — the switch-side interface name the client landed behind, on the AP's own Ethernet port), `hostname`, `deviceType`. This is the AP-behind-Ethernet-port case (a downstream wired device hanging off an AP's LAN port), a distinct and easily-conflated case from an ordinary access-switch wired client.

**Cisco 9800 client-oper YANG (`Cisco-IOS-XE-wireless-client-oper.yang`, primary vendored source):**
- `ewlc-client-dot11-oper-data` (L1800 ff.) — per-association 802.11 state keyed by `ms-mac-address`: `dot11-state`, `ms-bssid`, `ap-mac-address`, `current-channel`, `ms-wlan-id`, `vap-ssid`, `policy-profile`, `ms-ap-slot-id`, `radio-type`, `ms-association-id`, `ms-auth-alg-num`, `ms-reason-code`, `ms-assoc-time` (association timestamp — session-timing source), `encryption-type`, `security-mode`, `dot11-6ghz-cap`, `eht-capable`, `multi-link-client` — this is the richest single **capabilities + attachment** row in the corpus.
- `dc-client-info` (L~2640) — **device classification with per-attribute source protocol tracking**: `device-type`, `protocol-map` (bitfield naming which protocols contributed, `bit protocol-map-dhcp` etc. at L1318), `confidence-level` (uint32), `classified-time`, and then a repeated pattern of `<attr>` + `<attr>-src` pairs: `sw-version`/`sw-version-src`, `device-os`/`device-os-src`, `device-vendor`/`device-vendor-src`, `model-name`/`model-name-src`, `hw-model`/`hw-model-src`, `power-type`/`power-type-src`, each `-src` typed `dc-db-attr-type-e` (an enum naming the deriving protocol, e.g. `proto-dhcp`, `proto-dot11-device-analytics`, `proto-none`). **This is the standards-adjacent industry answer to "which fingerprint source produced which fact"** — see traps §6.
- `client-wsa-info` (near L2620) — a second, narrower fingerprint grouping: `client-mac`, `device-hostname`, `device-os`.
- `sisf-db-mac-entry` (L~2820) — `mac-addr` with an `ipv4-binding` container and `ipv6-binding` list (max 8), each carrying `zone-id` + `ip-addr`. **One MAC can hold multiple simultaneous IPv6 addresses** — a client's IP set is a list, not a scalar, at least for v6.
- `mmif-client-mobility-history-entry` (L2073) — `instance-id`, `ms-ap-slot-id`, `ms-assoc-time`, `role`, `bssid`, `ap-name`, `run-latency`, `dot11-roam-type`, `is-mlo-assoc` — this is the **roam event** row: no explicit "from AP" field, but the mobility history is a list, so from/to is derived by the caller from consecutive entries plus `role` (e.g. anchor/foreign) and `dot11-roam-type`.
- `username` (L2362) and `ms-username` (L2897, doc comment "Client username") — the wireless 802.1X/web-auth identity, separate leaves from `device-hostname`/`device-name` (L2630/2703, DHCP/mDNS-derived host identity) and `device-type` (L2650) — **three distinct identity-adjacent strings that must not be conflated**: reported hostname, human/account username, and classified device type.

**UniFi Network API (`spec/openapi/ubiquiti/unifi-network-openapi-v10.4.57.json`, primary vendored source, schemas `Wired client details` / `Wireless client details` / `Client overview`):**
- Both wired and wireless client detail schemas share a base (`Client details`, via `discriminator.propertyName: type`, mapping `WIRED`/`WIRELESS`/`VPN`/`TELEPORT`) with fields `id` (format `uuid` — **a UniFi-assigned stable identifier, distinct from the MAC**), `name` (string), `type` (string discriminator), `connectedAt` (date-time), `ipAddress` (string), `access` (nested discriminated object, `DEFAULT` vs `GUEST`, with its own doc comment explaining GUEST vs DEFAULT authorization semantics).
- The wired/wireless-specific extension then adds `macAddress` (string) and `uplinkDeviceId` (format `uuid` — the switch/AP device's own UniFi id, an entity ref, not a bare MAC).
- **This is the strongest direct evidence in the corpus that a production vendor already treats "client" as a UUID entity with MAC as an observed attribute, not the key** — `id` survives what `macAddress` does not (e.g., MAC rotation), and `uplinkDeviceId` is exactly a `DeviceGlobalRef`-shaped attachment pointer.

**Meraki Dashboard API `GET /networks/{networkId}/clients` (web-fetched, developer.cisco.com):** `id` (string — again a stable client identifier distinct from `mac`), `mac`, `ip`, `ip6`, `ip6Local`, `description` (short, likely user-editable label), `vlan` (name, not numeric id — string), `namedVlan`, `ssid`, `status` (enum `Online`/`Offline`), `firstSeen`/`lastSeen` (integer timestamps — the session-timing core fields), `manufacturer` (OUI-derived), `os`, `deviceTypePrediction`, `recentDeviceConnection` (enum `Wired`/`Wireless` — **one endpoint covers both attachment kinds, discriminated by this field**), `usage.sent`/`usage.recv`, `notes`, `user` (username), `switchport` (wired attachment), `recentDeviceMac`/`recentDeviceSerial`/`recentDeviceName` (the attaching device's identity, by three different identifiers at once), `wirelessCapabilities`, `smInstalled`, `adaptivePolicyGroup`, `groupPolicy8021x`, `pskGroup` (iPSK name — a per-client PSK identity scheme peculiar to Meraki/enterprise PSK deployments).

**Meraki wireless connection stats (web-fetched):** `GET /networks/{id}/wireless/clients/connectionStats` returns, per client, failed-attempt counts broken down by stage: `assoc`, `auth`, `dhcp`, `dns`, plus `success` — **this is a directly reusable four-stage connection-failure taxonomy** (association → authentication → DHCP → DNS) matching the domain brief's "connection failure stages" requirement exactly, expressed as a small closed set.

**Aruba Central `TenantClientHealth` (web-fetched, developer hub):** aggregate-only in the version fetched — `clientTypes[].name` (e.g. "Wireless") each with `health.groups[].name` (e.g. "Fair") and `.value` (count). **No per-client fields in this particular schema** — health scoring here is a network-wide rollup, not a per-client attribute; per-client health/RSSI exists in Aruba Central's UI and other endpoints but was not reachable with a verifiable schema this session (flag as unverified pending a working per-client endpoint fetch).

**Juniper Mist, RUCKUS One, TP-Link Omada:** the direct API-reference pages either 401'd or were not fetchable; only WebSearch's own aggregated summaries are available, and those are explicitly **unverified** per the brief's rule (no page fetched, no quote possible). Field name lists from those summaries (Mist: hostname, mac, manufacturer, os, ssid, ap name/mac, band, rssi, snr, idle/connected time, rx/tx rate; RUCKUS One: Mac, IpAddress, Ipv6Address, HostName, OsType, User, Status, RadioId, RadioMode, Channel, WlanId, Ssid, Snr, Rssi, RxByteRate, TxByteRate, ConnectedSince, Vlan) are directionally consistent with the verified Ruckus SCG proto and Meraki/UniFi fields above, but must be re-verified against a fetchable reference before being treated as load-bearing.

## 4. Proposed primitives (net/)

All of the following are ref-free values: they name a peer AP/switch/interface by string key (name or MAC), never by a `DeviceGlobalRef`, per the Primitives rule.

**`net/addr/v1` (extend, do not create a new package for this):**
- Add a `bool is_locally_administered` derivation is **not** a stored field — it is a pure function of `Eui48Address.octets[0] & 0x02`, and should be a helper/accessor in the generated-code layer or a service-side computation, not a schema field (storing a value that is 100% derived from another field in the same message the reader already has is exactly the mirror-drift Rule 1 warns against elsewhere in this codebase). Flag as an **open question** for the planner: does `net/addr/v1` gain a small non-stored helper (Go function `IsLocallyAdministered(mac Eui48Address) bool`), or does FlowSeer accept a stored, derivable field here as an exception? Precedent (`FdbEntry`'s CEL rule already computes unicast-vs-multicast from the same bit at validation time, without storing it) argues for the non-stored answer.
- No new address primitive needed: MAC is already `Eui48Address`; IP already `IpAddress`. Do not add a `ClientAddress` wrapper.

**New package `net/client/v1`** (peer of `net/wlan/v1`; the domain brief and the direction doc's package tree both reserve `net/wlan/v1` but not a client package — this is new territory to propose):
- `enum ConnectionMedium` — normalized, `CONNECTION_MEDIUM_UNSPECIFIED = 0`, `CONNECTION_MEDIUM_WIRED = 1`, `CONNECTION_MEDIUM_WIRELESS = 2`. (Meraki's `recentDeviceConnection` and UniFi's `type` discriminator both carry this distinction; FlowSeer should normalize it once rather than replicate two vendor enums.)
- `enum ConnectionFailureStage` — normalized, `_UNSPECIFIED = 0`, `_ASSOCIATION = 1`, `_AUTHENTICATION = 2`, `_DHCP = 3`, `_DNS = 4`. Directly modeled on Meraki's four-stage `assoc/auth/dhcp/dns` split (§3), generalized so a wired 802.1X failure also fits (association stage degenerates to link-up for wired).
- `WiredAttachment` (Primitive, no ref): `string switch_name` (peer key, like `interface_name` elsewhere), `string port_name`, `flowseer.net.switching.v1` VLAN id (reuse `vlan_id` validated `uint32`), `flowseer.net.protocol.???` — no, keep flat: `uint32 vlan_id`. Modeled directly on Ruckus's `ethIF` + `vlan` and UniFi's `uplinkDeviceId`+ (switchport not in the fetched wired schema, but Meraki's `switchport` string confirms the shape). **This mirrors `FdbEntry`/`NeighborEntry`'s "peer by name" shape exactly.**
- `WirelessAttachment` (Primitive, no ref): `string ap_name` (peer key), `flowseer.net.addr.v1.Eui48Address bssid`, `string ssid`, band/channel fields (reuse whatever `net/wlan/v1` lands with for `Bss`/`Radio` — do not duplicate; if `net/wlan/v1` is not yet built when this lands, define the minimal band/channel fields here and fold into `net/wlan` types later, flagging the duplication risk to the planner), `int32 rssi_dbm`, `int32 snr_db` (or noise floor + rssi, matching Ruckus's `rssi`/`receiveSignalStrength`/`noiseFloor` triple — **do not conflate rssi and "signal strength" as the same field; Ruckus's own schema treats them as two separate measurements**), rate/MCS/NSS fields, retry counters.
- `ClientCounters` (Primitive): rx/tx bytes, rx/tx frames, retries — modeled on Ruckus's counter set (both client protos share almost the same counter shape; factor into one message reused by both attachment kinds rather than duplicating per-medium, matching the direction doc's general preference for one shared counters shape per domain, e.g. `EthernetCounters`).
- `ClientFingerprint` (Primitive): the DHCP/HTTP/mDNS-derived classification values that are *reported facts about the client*, not the client's identity itself: `string dhcp_vendor_class` (option 60, raw string), `repeated uint32 dhcp_parameter_request_list` (option 55, raw ordered code list — **carry the raw list, do not pre-classify it into an OS guess in the schema**; classification is a service/ML concern per the doc-style "contract only" rule), `string http_user_agent`. This directly matches the brief's requirement and keeps the *observed bytes* (schema) separate from the *derived classification* (service). Registry pass-through note: DHCP option codes in the parameter-request-list are IANA-registered (BOOTP/DHCP option code registry) — treat `dhcp_parameter_request_list` entries as a registry pass-through numeric domain (`0..254`), not a normalized enum, matching the `IpProtocol`/`IpDscp` precedent in `net/packet/v1`.

## 5. Entity candidates (model/)

**`Client` — the answer to the "one shared shape" question.**

- **Identity key**: FlowSeer-assigned UUID (`ClientLocalRef.id`), exactly like `Device`. MAC is explicitly *not* the key — it is correlation data, the same role `serial`/`base_mac` play on `DeviceState` (see `device.proto` L120-131: "Serial and base MAC are correlation data the service merges sightings on, never the ref's key"). The evidence for this from vendor practice: UniFi's `id` (uuid) versus `macAddress`, and Meraki's `id` versus `mac`, are both already-shipped instances of exactly this split (§2). The correlation problem a FlowSeer Client-identity service must solve is harder than Device's: a device's serial+base-MAC pair is stable for the device's life, while a client's MAC can rotate per-SSID, per-boot, or on a timer (per §2's SLAP/randomization facts) — so the service needs a merge policy (e.g. "same MAC within one BSSID/VLAN scope inside a bounded time window is the same client instance; a locally-administered MAC seen fresh is a new candidate until 802.1X username or DHCP fingerprint correlation says otherwise"). **This merge policy is a service concern, not a schema fact — the schema only needs to make the key opaque and the observed MAC a repeatable, timestamped fact**, which argues for a list of observed addresses rather than one `mac` field on `ClientState` (see open question below).
- **Owning parent**: **none — top-level**, like `Device`. A client is not owned by the switch or AP it happens to be attached to right now (that would make roaming a delete+recreate of the entity, which breaks history and contradicts the domain brief's explicit ask for roaming *events*). `ClientLocalRef` holds only the UUID; `ClientGlobalRef` wraps just the `LocalRef`, following the `DeviceGlobalRef` shape exactly.
- **Config vs State split**: this is a **machine-observed entity nobody configures** in the ordinary case — nobody sets a client's MAC or hostname as intent. Per the conventions doc's "deliberately partial" rule, this family should probably be `Client` (plain, no `Config` suffix) + `ClientState` + `ClientEvent`, **not** the full triad — mirroring the pattern the conventions doc reserves for machine-observed entities. The one exception: an operator-assigned *label* or *guest access grant* (Meraki's `description`/`notes`, UniFi's `access.type = GUEST` with limits) is genuinely intended content a human sets, so a thin `ClientConfig` (display name override, static/reserved IP or VLAN assignment, guest authorization) may still be warranted — **flagging this as the open question it is**, because whether that config surface exists yet is a product-scope decision, not a schema-shape one.
- `ClientState` should hold: the *current* best-known observed identity read (hostname with is-it-fresh semantics, fingerprint, classified device type/vendor/OS with confidence, matching Cisco's `dc-client-info` shape but flattened to FlowSeer's presence/absence convention rather than Cisco's per-field `-src` pattern — see traps §6), lifecycle (`ClientLifecycle`: e.g. `ACTIVE`/`STALE`/`RETIRED`, mirroring `DeviceLifecycle`'s three-state shape), and **the current attachment** (`ConnectionMedium` plus one of `WiredAttachment`/`WirelessAttachment`, structured as a `oneof` the same way `Interface.kind` is a required oneof — a client is wired *or* wireless right now, never both, even though it may have been the other yesterday).
- `ClientEvent` covers at minimum three transition shapes the domain brief calls out: a lifecycle transition (mirrors `DeviceEvent`'s `from`/`to`), a **roam event** (`from_attachment`/`to_attachment` using the same `WirelessAttachment`/`WiredAttachment` primitives, plus a normalized roam reason enum — Cisco's `dot11-roam-type` and the mobility-history's `role` are the vendor evidence this needs its own small enum rather than a free string), and a **connection-failure event** (`ConnectionFailureStage` plus enough context — SSID/BSSID attempted, or switch/port attempted — to diagnose it, directly satisfying Meraki's connection-stats stage taxonomy from §2 turned into an event rather than an aggregate counter).
- **Session-stats history** (RSSI/SNR/rate time series, byte/packet counters over time) is explicitly **not** State — State is "what is observed *now*." A `ClientCounters` reading is more naturally either (a) a periodic sample carried on `ClientEvent` variants the ingestion pipeline emits, or (b) a store/telemetry concern outside the wire schema entirely (matching how `net/capture` keeps `CaptureCounters` a value type consumed by services, never accreted inside an entity's State). **Flagging as open question**: does FlowSeer want a `ClientState.counters` snapshot field (cheap, last-known-value semantics, matching `DeviceState`'s pattern of holding the latest read) in addition to timeseries living elsewhere? Recommend yes for the current snapshot only, mirroring `DeviceState`.

**Discovery's ARP/FDB-observed host — same entity, different provenance, no separate family.** An ARP/FDB row is `net/ip/v1.NeighborEntry` / `net/switching/v1.FdbEntry` (already-landed primitives) discovered on a *Device's* State — it does not carry a hostname, fingerprint, or 802.1X identity by itself. The entity question is: when discovery correlates "this MAC showed up in an FDB row on switch X, port 3" into something worth tracking as a *host*, is that the same `Client` entity the wireless side produces, or a separate `DiscoveredHost`? **Recommendation: same entity.** The evidence: Meraki's own `clients` API already unifies wired and wireless under one schema discriminated by `recentDeviceConnection`; UniFi does the same via its `type` discriminator (`WIRED`/`WIRELESS`/`VPN`/`TELEPORT`). A wired client discovered only via FDB (no DHCP, no 802.1X) is simply a `Client` whose `ClientState` has an empty fingerprint and an unknown hostname — not a different kind of thing. The FDB/ARP row itself stays exactly what it is today: a device-scoped table entry with no ref, and the *correlation from FDB row to Client entity* is a service job (the same job Device's serial/base-MAC merge already is), not a new schema message.

## 6. Traps

- **RSSI vs "receive signal strength" vs SNR vs noise floor are four different numbers, not synonyms.** Ruckus's `APClientInfo` carries `rssi`, `receiveSignalStrength`, and `noiseFloor` as three separate `int32` fields with three separate doc comments (§2) — a schema that collapses these into one `signal` field loses information a real vendor keeps distinct. Units are also not uniform across the corpus: dBm is the norm for RSSI/noise floor, but the domain brief's own list ("RSSI, SNR") and the wireless-atlas prior survey both flag transmit power as reported "variously in dBm, mW, and as a percentage of maximum" (`08-wireless.md` L169) — the same caution applies to signal-quality fields; verify per-provider units before normalizing rather than assuming dBm everywhere.
- **IPv6 cardinality is not scalar.** Cisco's `sisf-db-mac-entry` models `ipv6-binding` as a `list` (max 8) while its IPv4 binding is a single container, and Meraki exposes both `ip6` and `ip6Local` as separate scalar fields (global vs link-local, not "the" IPv6 address). A `Client` schema with one scalar `ipv6_address` field will silently drop real, simultaneously-valid addresses.
- **Per-field provenance vs FlowSeer's envelope-only provenance rule.** Cisco's `dc-client-info` names, for almost every classification attribute, which protocol produced it (`sw-version-src`, `device-os-src`, `device-vendor-src`, ...) — a materially richer provenance model than FlowSeer's current rule that provenance "rides the envelope" and "is never a field of an `<Entity>State`" (`docs/conventions/protobuf.md`, "Provenance rides the envelope"). A `Client`'s fingerprint genuinely needs multi-source attribution (DHCP said one OS, mDNS said another, HTTP UA said a third) in a way a device's `sys_object_id` never does, because a device typically has one authoritative source per fact while a client's identity is inferred from several imperfect signals that can disagree. **This is a real tension for the planner to resolve, not a fact this dossier can settle**: either (a) accept envelope-level provenance and let the *service* merge conflicting signals before writing `ClientState` (simplest, consistent with the existing rule, loses per-fact attribution), or (b) treat each fingerprint source as its own event stream and let `ClientState` hold only the merged result (defers the conflict to event history, still consistent with the rule), or (c) grant `Client` a documented, reviewed exception to hold per-attribute source tags (breaks the existing rule's uniformity). Do not default to (c) without an explicit decision — it is the option the conventions doc's "no message carries an observed_at or a binding" worked-example line was written to prevent (device.proto's example comment, `docs/conventions/protobuf.md` "A worked example" section).
- **Randomized-MAC detection is a derived bit, not a stored fact — but "is this the same randomized client as yesterday" is a much harder unsolved problem than the bit itself.** The U/L bit tells you a MAC *is* locally administered; it tells you nothing about whether two locally-administered MACs seen on different days are the same physical device. Do not let a schema field named anything like `is_randomized` imply more identity confidence than the bit actually carries.
- **"Client" behind a client — layered relays.** Ruckus's `cpeMac` field (a MAC address *behind* the reporting client) and the wired-client-on-an-AP-port case (`ap_wired_client.proto`) are both real, filed-away edge cases in the corpus: a client entity can itself have a downstream client hanging off it (a CPE gateway relaying one wireless station's traffic for a whole LAN behind it). A `Client`/`WiredAttachment` model that assumes the attaching device is always the network infrastructure (an AP or a switch), never another client, will mis-model this.
- **VLAN as a name vs VLAN as a numeric id are both live in production APIs.** Meraki's client `vlan` field is a *name* string plus a separate `namedVlan`; Ruckus's `vlan` is `int32`. FlowSeer's own `vlan_id` predefined validator (`net/switching/v1/vlan_id.proto`) is numeric — fine as the schema's canonical form, but adapters converting from Meraki must resolve the name to a number themselves; do not assume every provider hands you the numeric VLAN directly.
- **The connection-medium discriminator is not always reliable at the moment of observation.** Meraki's `recentDeviceConnection` is explicitly the *most recent* connection type, implying a client can flip between wired and wireless over its lifetime (e.g., a laptop docked then undocked) — this reinforces that `Client` must be medium-agnostic at the entity level with medium living only in the current `ClientState.attachment` oneof and in each `ClientEvent`, never as a top-level Client property.
- **The `dot11StationConfigTable`'s `INDEX { ifIndex }` is a trap for anyone skimming the MIB name.** It is not a table of *associated peer stations* — it is the *local radio's own* station configuration (its own `dot11StationID`). The wireless-atlas's own note about `CAPWAP-BASE-MIB::capwapBaseStationTable` being the actual IETF standard for the associated-station case is confirmed by this session's read of `IEEE802dot11-MIB` line 152-209 and should be trusted over any assumption that "the 802.11 MIB has a client table."

## 7. Open questions for the planner

1. Does `Client` get a `ClientConfig` (guest authorization, static VLAN/IP assignment, display-name override) now, or is it deferred until a concrete product requirement names one? (§5)
2. How is per-field fingerprint provenance (Cisco's `-src` pattern) reconciled with FlowSeer's envelope-only provenance rule — accept service-side merge before writing `ClientState`, defer conflicting signals to `ClientEvent` history, or grant a reviewed schema exception? This is the single highest-leverage decision in this dossier; see traps §6. (§6)
3. Should `net/wlan/v1` (currently reserved, unbuilt per the direction doc's package tree) be built *before* `net/client/v1`'s `WirelessAttachment`, so band/channel/BSS types are defined once and shared, or should this dossier's minimal band/channel fields land first and get folded into `net/wlan` later? Building `net/wlan/v1` first avoids a near-certain near-term duplication. (§4)
4. Does `ClientState` carry a `counters` snapshot (last-known byte/packet/retry counts, mirroring `DeviceState`'s "latest read" pattern), with time-series history left entirely to a store/telemetry layer outside the wire schema — or does FlowSeer want no counters on the entity at all? (§5)
5. Is `is_locally_administered` (and by extension `is_randomized`-adjacent facts) purely a derived accessor with no schema field, matching the `FdbEntry` unicast-bit precedent, or does the planner want it stored for query convenience despite being 100% computable from the MAC already on the message? (§4)
6. Does the wired-behind-AP case (`ap_wired_client.proto`'s `APWiredClientInfo`) get modeled as an ordinary `Client` whose `WiredAttachment.switch_name` happens to name an AP, or does it need its own discriminator so consumers can tell "wired client on real switch infrastructure" from "wired client relayed through an AP's LAN port"? (§6)
