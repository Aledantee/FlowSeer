# netpen OSPF Attacker Router ID - Plan

> Needs-decisions: the router-id constant is a one-character fix, but correcting
> it forces the OSPF fixtures to change, and a fresh `go run harvest_routing.go`
> produces zero checksums on the lsa-update/flush/goodbye frames where the
> committed fixtures carry valid ones. How the committed fixtures are meant to be
> regenerated — and whether the Go harvest generator is the canonical source or
> carries a checksum gap — must be settled (U1) before the fixtures are rewritten.

## Goal

Make netpen inject the OSPF attacker router ID it intends and documents,
`10.0.0.99`, so `netpen_t2` `TestT2OSPFLiveLab` passes end to end against the
IOS-XE lab (the spoofed neighbor appears as router ID `10.0.0.99`, matching the
tier's `ospfAttackerRouterID`) and the `ospf` VALIDATION_MATRIX cells record real
vendor truth. The means is correcting the constant in the behavior and the
fixture generator and regenerating the OSPF fixtures without regressing their
checksum validity. This plan is wrong if the committed OSPF fixtures are not
produced by `harvest_routing.go` at all (then the router-id fix needs whatever
tool did produce them, and U1 routes that back as a blocker).

## Background evidence

Found during the flowssh live validation (2026-09-25). Against IOS-XE the
injected OSPF neighbor appeared as router ID `10.0.0.153`, address `10.0.0.99`,
where the tier expects router ID `10.0.0.99`:

- `src/edge/netpen/attacks/routing/helpers.go:36`:
  `attackerRouterID uint32 = 0x0a000099 // 10.0.0.99` — but `0x99 = 153`, so the
  value is `10.0.0.153`. `10.0.0.99` is `0x0a000063`. The source IP is correct:
  `attackerIP = net.IPv4(10, 0, 0, 99)` (helpers.go:38).
- `ipToRouterID` (`src/edge/netpen/attacks/routing/ospf.go:425`) formats the
  uint32 dotted-quad, so the wire and the IOS-XE neighbor table show `10.0.0.153`.
- The tier asserts `ospfAttackerRouterID = "10.0.0.99"`
  (`src/edge/netpen/test/integration/t2_lab_ospf_test.go:17`), matched by router
  ID via `HasNeighbor` (`lab/iosxe.go`), so the live neighbor does not match.
- The same constant is duplicated in the fixture generator
  `src/edge/netpen/attacks/routing/harvest_routing.go:58` (`//go:build ignore`).
- `TestOSPF_FixturePins` (`src/edge/netpen/attacks/routing/routing_test.go:120`)
  byte-compares the runtime OSPF TX against `attacks/testdata/routing/ospf.pcap`
  and `ospf_restore.pcap`, so any wire change requires regenerating those.

Attempted-and-reverted probe (2026-09-25): editing both constants to `0x0a000063`
and running `go run harvest_routing.go` regenerated the fixtures but then
`TestOSPF_ChecksumValid` failed ("OSPF checksum is zero") on the fixture
lsa-update/flush/goodbye frames, and `TestOSPF_TeardownOrder` failed because the
runtime flush/goodbye frames now carried a non-zero checksum (byte 46 `0xea`)
while the regenerated fixtures carried `0x00`. On the clean tree both tests pass.
So the committed fixtures carry valid checksums the fresh Go harvest does not
reproduce — the divergence U1 must explain. Related: netpen's OSPF zero-checksum
bug noted in memory `project_eveng_lab_injection`.

## Decisions

- The router ID becomes `0x0a000063` (`10.0.0.99`) in both the behavior
  (`helpers.go`) and the generator (`harvest_routing.go`). Why: the comment, the
  source address, and the `netpen_t2` assertion all intend `10.0.0.99`; the hex
  is the defect. Both must change together or `TestOSPF_FixturePins` fails.
- The OSPF fixtures are regenerated by the project's canonical mechanism, not
  hand-patched byte-by-byte. Why: hand-patching four bytes of router ID also
  requires recomputing each affected OSPF checksum by hand, which is exactly the
  error the fixture pins exist to catch. The canonical mechanism is decided in
  U1.
- Whatever U1 finds about the checksum divergence is fixed so the generator and
  the runtime agree (both valid, non-zero), rather than weakening
  `TestOSPF_ChecksumValid`. Why: a zero OSPF checksum is invalid on the wire and
  a live IOS-XE peer may reject it; the tier's whole point is a peer that
  accepts the injection.

## Requirements

1. netpen injects OSPF router ID `10.0.0.99`. Acceptance: a unit test on the
   OSPF hello TX decodes router ID `10.0.0.99`; `ipToRouterID(attackerRouterID)`
   is `"10.0.0.99"`.
2. `TestOSPF_FixturePins`, `TestOSPF_ChecksumValid`, and `TestOSPF_TeardownOrder`
   pass with the regenerated fixtures — every OSPF frame's checksum non-zero and
   valid. Acceptance: `go -C src/edge/netpen test ./attacks/routing/...` green.
3. `TestT2OSPFLiveLab` passes against the IOS-XE lab: neighbor `10.0.0.99`
   appears and clears. Acceptance: the live run passes (lab wired per memory
   `project_flowssh_iosxe_blocker`; recreate Kali `eth1.999`).
4. The `ospf` VALIDATION_MATRIX `t1 AE6` and `t2` cells carry the dated live
   result. Acceptance: cells cite the run date and finding-class, not
   `pending live run`.

## Out of scope

- The injector-side `sudo netpen` PATH issue (netpen at `~/netpen`, not in
  `secure_path`, redundant with its `setcap`): note it, but the tier's
  `NETPEN_LAB_INJECTOR_SUDO_PASSWORD`/sudo design belongs to the 2026-09-23 plan.
- Non-OSPF routing behaviors (eigrp, wpad), except that their fixtures must not
  regress when routing fixtures are regenerated.
